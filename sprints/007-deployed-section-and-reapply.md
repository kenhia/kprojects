# Sprint 007 — The "Deployed" section, and the re-apply pass it needs

2026-08-15 · korg proposal 1278 · covers #857 · handoff korg:1282

## Goal

Two halves that share a proposal because the second cannot land before the
first. Make `Deployed` a default section of the sprint-record convention
(#857), then push the current installer's block out to the **14 repos across
kai, kubs0 and cleo still carrying the retired bash installer's** — five of
them Rust repos being told to reach for `uv`, `ruff` and `ty`.

The ordering is not tidiness. The re-apply command builds kprojects from
`git+https://github.com/kenhia/kprojects`, i.e. from **main**, so re-applying
before #857 merges would hand all 14 repos a pre-#857 block and buy a second
pass.

## Decisions

- **#857's second bullet had no target, and the sprint says so rather than
  inventing one.** The work item asserts the deploy expectation is "stated
  twice: once in the sprint-record convention and again in the harness
  instruction block", and asks for the redundant copy to be deleted from
  `harness/instructions.md`. It is not there and never has been — every `.md`
  in the repo was searched, and `instructions.md` as it stood on 2026-08-01,
  the day #857 was written, carried exactly one deploy mention: `just deploy`
  (or variants) if the project deploys`, which is about the justfile recipe.
  The real second copy is **sprint-ship Step 7.3** in `agent-skills`, which
  spells out "append a short 'Deployed <date>' section … (see the repo's
  convention)". That is a different repo and a different korg project, so it
  gets its own work item rather than a drive-by edit on this branch. Ken's
  call.
- **The section is scoped to projects that deploy.** "Every sprint record ends
  with Deployed" would put an empty heading in kprojects' own records, and this
  repo does not deploy — it is installed via `uvx` from git. A convention that
  is inapplicable to the repo defining it is a convention nobody trusts.
- **What goes in it mirrors what sprint-ship already collects** — what shipped,
  where, when, what was verified live. That is the point of the addition: once
  the convention owns the shape, Step 7.3 can shrink to naming the section
  instead of describing it.
- **"Appended after the deploy, not predicted before it."** The rest of the
  record is written *during* the sprint; this one section cannot be, because
  the deploy happens after the squash-merge. Saying so inline stops the section
  becoming an intention.
- **Verification scope for the re-apply pass: light proof everywhere, full
  `just check` on tier 1 and wherever `.gitignore` changed.** Ken's call, and
  the handoff's own suggestion. The light proof is strong — the diff shows only
  the block, and re-running the installer leaves an empty `git status`, which
  is the idempotency property batch 1 verified directly. Full gates on all 14
  means minutes of Rust build five times over to assert something the change
  cannot break; skipping them entirely would leave the tier-1 repos, the ones
  whose guidance was actively wrong, unproven.
